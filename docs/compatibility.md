# 兼容性、设备身份和迁移

| 项目 | 已知范围 |
| --- | --- |
| 实体灯 | 一台广播名符合 `LFFL01-P-XXXX` 的徕芬双路大路灯；未取得可可靠比对的固件版本 |
| 同型号另一台 | 设计为按名称发现、从状态读取身份；已用合成不同身份测试，尚无第二台实体验证 |
| 其他型号 | 不支持，不能因为有 FF01/FF02 就认为协议相同 |
| 已实测桥接主机 | Mac mini M4、macOS 27、独立 Node 24.21、Python 3.12.14 |
| 其他 Mac / Intel | 安装路径不写死、依赖按平台安装；未逐机验证，最低系统版本也受 Python/PyObjC 支持范围约束 |
| Linux | Bleak 有后端，依赖排除 macOS 专属包；只提供实验性前台运行，未验证 BLE/Avahi/服务权限 |
| Windows | 本安装器及后台管理未支持；早期仅有 BLE 服务发现，不代表桥接端到端支持 |
| Apple 自适应照明 | 实测在下灯入口启用，按下灯亮度计算整灯共用色温；需 Apple 家庭环境支持该功能 |

## 为什么不要求手填 MAC

macOS CoreBluetooth 扫描返回本机分配的 UUID，不直接返回 App 里的蓝牙 MAC。同一灯在不同 Mac 上可能有不同 UUID。向导按完整广播名查找，连接后检查服务和已知 43 字节状态；状态内包含灯自己的协议地址。运行时同时核对名称和这个协议地址，再允许控制。

发现两个同名设备时拒绝随意选择，用户必须指定扫描候选。预检不访问 DFU，不尝试未知服务写入。上述检查是避免误控/错解包的边界，不是厂商型号认证，也不是密码学身份认证。

相关平台行为见 [Bleak macOS 文档](https://bleak.readthedocs.io/en/latest/backends/macos.html)。

## 是否加密/绑定

分析的应用命令中未观察到设备专属密钥、挑战应答或登录令牌。序号为单字节计数，末字节 XOR 用于差错校验；已在多个断线重连会话中独立控制，不需要徕芬 App 在线。

这只描述已观察的应用层。不能由此断定链路层未加密，不能保证其他固件不要求 BLE bonding 或新增鉴权。HomeKit 自己的配对与加密仍由 HAP/Homebridge 处理，与灯的 BLE 命令是两回事。

## 新设备验证顺序

先记录原状态。通过向导状态预检后，逐项验证：总关/开；上灯独立关/开；下灯独立关/开；上灯和下灯亮度；共用色温；自动亮度暂停和恢复。每次检查真实发光，不以 ACK 或 HomeKit 图标替代实体观察。没有真实灯时，单元测试通过只能说明程序逻辑回归通过。

固件已观察的两个细节：

- 全关时，独立开灯命令可能有成功 ACK 但灯不亮。桥接会先总开，再关闭不需要的一路，另一边可能短暂点亮。
- 部分点亮时，重复总开命令不补开另一边。桥接通过独立开关补开关闭的一路。

原生自动亮度控制整灯；分控关闭时若仍运行，曾出现状态称关闭但下灯缓缓重新发光。因此桥接先暂停该模式，保持用户偏好，全开后才恢复。

## 换电脑

最简单的方法是在新电脑重新安装/扫描/配置，再将新桥接加入家庭；这会生成新的桥接身份，原有场景/自动化要重新关联。旧电脑桥接必须停止，避免抢占同一蓝牙连接。

需要保留配对时，请私密备份整个旧运行目录，至少包含 `homekit/storage`、`homekit/logs/ble.jsonl.preferences.json`。新主机先独立安装同版本依赖，再在停止状态迁移 storage；修改配置里的 Python/worker/log 绝对路径，重新扫描确认设备、清除旧主机专属 identifier。只有同一桥接身份和完整持久数据都保留才可能延续配对；本项目尚未完成第二台 Mac 的迁移实测，不承诺无须重新配对。

不要把含密钥、PIN、家庭身份和日志的运行目录上传公共仓库。源码压缩包不包含这些数据，也不应包含预装 venv 或 node_modules。
